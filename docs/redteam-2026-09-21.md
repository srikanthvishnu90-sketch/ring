## 2. Approval atomicity — PASS (3/3)

## 3. Auth bypass — MIXED: authn PASS, authz FAIL (critical)

- `GET /api/memories`, `GET /api/export`, `DELETE /api/account` with no token → 401 `missing authorization token`. With garbage token → 401 `invalid or expired token`. PASS.
- Body `userId` spoofing in `/api/chat` is neutralized: `optionalUser` always sets `req.userId` ('local' unauthenticated), and `req.userId || req.body?.userId` means the body value can never win. PASS.
- **FAIL — `POST /api/approvals/:id/resolve` has NO authentication and NO ownership check.** Verified: unauthenticated decline returns 200. Combined with unauthenticated `/api/chat` (identity 'local'), a remote caller can create a held `gmail_send` card as 'local' and then approve it — `resolve()` executes `executeTool(rec)` with the record's userId, which resolves to the real connected Gmail OAuth tokens → **unauthenticated real email send**. The approve branch was NOT fired (would have sent a real email); the chain is verified up to the execution call in code (`approvals.js` `resolve()` → `executeTool(rec)` on approved).
- **Fix required before any production exposure:** add `requireUser` to the resolve route AND check `rec.userId === req.userId` before executing; also gate `/api/chat` tool-holding behind `requireUser` or scope held cards to the authenticated user.
